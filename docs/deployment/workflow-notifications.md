# Workflow notification operations

Apply notification01, approvals02, maintenance03 in that order, then deploy the application. All existing boards default to scheduling off and UTC; approvals and in-app source alerts do not require reminder opt-in. The runtime producer flag starts false to allow a controlled compatibility rollout. After verifying the application, run `workflow-scheduler.sql` to activate source producers and the two five-minute jobs.

The generator runs inside PostgreSQL independently of HTTP/email. It serializes timer runs and locks boards, cards and approval requests in UUID order, re-reading state after the board lock. Deadline phases use local calendar dates, with review requests retaining their original timezone. A Monday deadline becomes overdue Tuesday and escalates Wednesday; late opt-in produces both overdue and escalation once. Assignment/date counters and request IDs deduplicate source versions. There is no REST row cap.

The public maintenance POST accepts no target or payload. A service-only database gate allows one maintenance batch per minute across instances; each batch claims at most 25 deliveries. Each delivery has a two-minute lease. The worker has a 20-second transport budget and a three-second provider timeout. A crash or timeout may leave an ambiguous acknowledgement: retry uses the same frozen sender, recipient, subject, body and provider idempotency key. At 23 hours after the first attempt, pending/expired work stops for inspection rather than risking a resend beyond the provider's 24-hour deduplication window. Automatic retries are capped at six attempts with exponential backoff. Owner retries allow only definitive transient failures still inside the same safe window, resetting attempts but preserving payload, key and first-attempt timestamp.

Current board access, opt-in, assignment/date/request revision and completion are checked before claiming and again immediately before transport. In-app notification reads keep legitimate history visible only while the recipient retains board access. Actor self-alerts are suppressed. A disabled/missing sender, missing recipient email or recipient opt-out is recorded as disabled, never accepted. A provider acceptance is not proof of inbox delivery. Owner health exposes only counts; no recipient addresses, provider response bodies or credentials are returned.

Once producers are active, assignment and comment/mention events are captured in the original source transaction. Compatibility helpers become no-ops; old notification INSERTs without a source event key fail before old application code can send email directly. Retain this protection during application rollback. Disable the two workflow cron jobs to stop new scheduled generation/wakeups without deleting requests, history, source alerts or outcomes. Do not alter the separate audio maintenance job.

The existing bearer-authenticated daily cron URL delegates to this same worker. It no longer sends its own due-date email. Scheduler credentials and extra dependencies are not required. Production email remains disabled until `RESEND_FROM` is configured with a verified sender; this release does not send live QA email.

Verification: focused tests exercise source rollback/dedup, legacy overlap, mention precedence, revoked reads and privileged grants, >1,000 tasks, repeated schedules, overdue/escalation, due changes, stale assignment cycles and approval decisions, frozen review timezone, lease recovery/frozen payloads, ambiguous delivery cutoff, disabled email, safe retry, endpoint authentication, public gate and provider timeouts/errors. Native PostgreSQL concurrency and production scheduler checks belong to the integrated rollout proof.
